# Open problems

> **In short.** Everything known to be wrong or missing, so nobody rediscovers it, filed by what it would take to fix: values makers do not publish; sources that conflict, cannot be read or cannot be reached; what the model and the tools cannot do; and what needs a person, the owner or a test. The counts below are re-derived from the build. Each item keeps the query behind its own figures, and its old section number as a stable name, so a reference to §N elsewhere still finds it.

What the database holds is counted in [build/snapshot/counts.md](../build/snapshot/counts.md). This page is what it
does not hold, or holds with a known doubt, so that a reader can tell a gap someone is working on from one nobody has
noticed.

**How to read it.** Sections 1 to 29 and 35 keep their numbers. Sections 30 to 34 and 36 to 39 were each "what one round left open";
their items are filed by subject as §30.1, §30.2 and so on, each opening with the round it came from, and keep that
round's figures as its history. The counts in the table are today's (`npm run docs:open-problems` writes them at a
round's close). The table at the end says where every section went. `npm run sql -- --snapshot "<query>"` answers an
item's query from the SQLite file as written; without `--snapshot` the file is rewritten first when it is older than the
tables, and `npm run sql -- --build` builds first.

Two things this page is not. It is not the check list: every rule the build enforces is in [RULES.md](RULES.md),
generated. It is not the history of the work: what each round found is in [audits/](audits/), and the coverage
campaign's open targets are in its [status page](audits/2026-09-30-coverage-expansion/STATUS.md).

### 40.2. The importer costs more to run than its rules need

*From research intake 2, 2026-10-20 (m488 to m494; D178; [record](audits/2026-10-20-research-intake-2/README.md)), a read-only review the owner asked for; nothing in the importer was changed.*

**The judgement: the importer's rules are right and its tooling has grown accidental.**

These are essential and should stay:
- bytes by SHA-256;
- every quote checked on the cached page;
- a named reviewer;
- migrations as the only history;
- the rehearsal gate before a batch writes;
- a blind second read of what decides;
- a private byte store.

The rest has grown round by round:
- **Size.** `scripts/ingest/` is 11,906 lines in 27 files: 4,686 on 2026-09-20, touched by 121 commits since. It has 19
  `ingest:*` commands, and IMPORTING.md documents about 40 command forms.
- **The documented path is unused.** No batch since b40 has gone through `propose` → `batch` → `applyBatch`. Every batch
  since (b41 to b50) wrote its own `build-bNN.mjs`: 2,420 lines in ten scripts, the row builder copied three times. Glue
  code written for one round since 2026-10-04 comes to about 4,200 lines.
- **One document needs two formats.** A new document is registered through the JSON proposal path and its values travel
  the CSV reading path. That takes:
  - two migrations;
  - placeholder product keys;
  - a lint exemption between the two migrations;
  - adapter scripts.
  This round needed the same again: `intake.mjs`, `build-b50.mjs`, `second-docs.mjs`, `review-r2.mjs`, m488 and m489.
- **Repeated logic.**
  - Six migrations copy `apply.mjs`'s rehearsal.
  - 22 switch ledgers through `H2C_INGEST_ROOT`.
  - The quote check exists in at least five forms.
- **What it cannot see or rerun.**
  - The STATUS, BLOCKERS and READINGS reports see only the first ledger.
  - A batch migration cannot run again without restoring the private store.
  - The source rows the batch builder writes do not know the newer columns, such as Superseded by (this round's
    rehearsal caught it).

**Options, best first.** None was built.
1. One proposal format and one applier: the CSV path also adds sources and grades, under the guard's refusal codes. Each
   batch then needs one migration.
2. A shared `applyRound()` for batch migrations, so each is about 15 lines.
3. A generic `ingest:intake --package <dir>`, with reviewer decisions in an `overrides.csv` (action, row, reason, who)
   instead of code.
4. One ledger, or a registry the reports read in full.
5. Retire the unused rule-based batch modes, and rewrite IMPORTING.md to the path rounds actually use: about 8 commands.
6. Housekeeping:
   - move the living reading specs from the reader-round folder to `scripts/ingest/`;
   - take a `--package` argument instead of absolute paths;
   - fold the source and packet exports into `round:close`.

Options 1 and 2 remove most of a round's glue. Their risk is medium and low: the guard's tests pin its behaviour.

### 1. Measurements published without a test method

**Closed on 2026-09-21 by m101**, which corrected 70 rows across 19 sources. What is left is not damage.

The 74 rows this section counted held a fragment of the neighbouring column instead of the test method: the tail
of a Subject ("Transition Temperature"), the head of a Testing Method ("DSC,", "ISO 179,", "ASTM"), or the
direction that followed it ("(X-Y)"). Bambu Lab's properties table is `Subjects | Testing Methods | Data` and
the original extraction cut it in the wrong place; Polymaker prints a method once between a property's two
direction rows, and the second row kept only its first word. The values were never affected — they come from the
Data cell and reconcile against their raw text on every build. Each of the 70 was re-read from its own cached,
hash-checked source, matched to its sheet row by its property, its direction and its load, and given the method
that row prints (D35).

**Rows read and deliberately left as they stand, because the fragment is what the sheet prints** (twenty on
2026-09-21; 36 live on 2026-10-07, as later Prusament sheets entered):

| Rows | Source | What the sheet prints |
|---:|---|---|
| 8 | Polymaker's PolyLite, PolyMax, PolyMide, PolySonic and Polymaker sheets | `N/A` in the Testing Method column, for thermal conductivity (two more are retired copies) |
| 23 | 15 Prusament sheets, PVB's five among them | `Prusa Polymers` — Prusa's own measurement, for density, moisture absorption, hardness and interlayer adhesion |
| 5 | iSANMATE PLA-GF and PA6-CF | a bare `ISO`, beside four values and nothing more |

A sheet being vague is not transcription damage, and a standard nobody read off a sheet is exactly what this
database exists not to hold. The same applies to the `Method A` / `Method B` rows this section used to count
separately (six then, 26 on eight Siraya sheets now): Siraya Tech prints "Method A/B" beside a pair of heat deflection temperatures and names no standard,
and the load each row was measured at is typed in `Test load MPa`.

```bash
npm run sql --silent -- "select sourceid, standard_load, count(*) n from measurements
  where standards_state = 'Not published' and standard_load in ('Modulus','Strength','Elongation','Deflection',
  'Temperature','Transition Temperature','(X-Y)','DSC,','ISO','ISO 179,','ASTM','N/A','Prusa Polymers')
  group by 1, 2 order by n desc"
```

Twenty-five batches of imported sheets have added none of this damage: `scripts/ingest/propose.mjs` reads a
standard by its own designation and writes the sheet's words, and `PARSE-MISMATCH` fails a row whose typed
`Standards` and raw text disagree.

### 9. The column beside the printing table

**Closed on 2026-09-21 by m102**, which corrected 130 cells across 31 profiles.
