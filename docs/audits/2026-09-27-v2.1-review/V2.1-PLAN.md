# Version 2.1: implementation-ready plan

> **Historical record** (2026-09-27): written for one review or round. It describes the tool and its data as they were then; numbers, rules and file names may have changed since. For where things stand now, read the [README](../../../README.md) and [OPEN-PROBLEMS](../../../docs/OPEN-PROBLEMS.md).

Proposed from the review of commit `eb695b8328b369986341491d948d793abdfcb995`, 2026-09-27. No changes in this plan have been implemented. The owner must authorize implementation and any direction changes; a planning agent may refine this package without editing the reviewed repository.

## 1. Product outcome and scope

Version 2.1 should complete a narrow engineering workflow: **part question → evidence-based material shortlist → specific feasible product and state → traceable print/test handoff**. It should preserve the offline single-file tool and canonical authoring workflow. It should make unknown evidence operational by saying what to check next.

Primary audience: a small engineering team with an H2C, capable of reading a data sheet but not expected to know the database's historical rules. A novice-friendly starting path is useful; structural design calculations, generic consumer recommendations and certified allowables are outside this release's promise.

Priorities, in order:

1. Make product decisions, state compatibility, exposure applicability and print feasibility true.
2. Make the shortlist reproducible and independently testable.
3. Close targeted data gaps that change real scenarios.
4. Let the user reach passing products and their recipes quickly.
5. Improve debug/authoring operations and keep verification inside its budget.

The record tier still captures broader source content cheaply. Volume goals belong there; decision-tier goals count requirements settled and actionable products. Do not mix the two.

## 2. Decisions to settle before coding dependent behavior

## 3. Target architecture

Keep the source → compile → engine → render structure. Add explicit applicability and state contracts through the existing schema/data/build layers, rather than introducing an independent second database of decision facts.

```text
Registered source bytes/page witnesses
  ├─ Decision records: value + scope + conditions + typed role + provenance
  └─ Record content: as-published facts and maker narrative, cheaply captured
            ↓ schema, witness and cross-record gates
Canonical CSV tables + vocabularies + review records
            ↓ deterministic core compiler
Product/state decision inputs + separately labeled material/polymer context
            ↓ optional existing estimate overlay
Pure selection engine → one evaluation and ranking result
            ├─ material rollup with pass/fail/unresolved counts
            ├─ exact product/state reasons and supporting record IDs
            └─ gaps, treatments and next verification tasks
            ↓
Offline table / chart / compare / product cards / export / decision brief
```

### 3.1 Data changes: conceptual contract, not a premature schema prescription

An implementation agent must inspect current table schemas and reuse existing fields before adding tables/columns. Keep raw words; do not normalize away conflicting evidence. The following facts need explicit homes:

- **Evidence applicability:** grade/formulation/material/polymer/context scope; applicable IDs or one relation row per target; reviewed applicability basis and source locator. An existing GradeID is not permission to apply its record to every product of the material.
- **Product state:** product ID, post-processing state/schedule, moisture state/condition, print orientation, and recipe provenance. A state signature can be derived from existing typed conditions; only nonderivable assertions need authoring rows. Do not duplicate every measurement into a state table.
- **Exposure:** source agent/category, concentration or stated missing state, temperature, duration and test/claim type. Use existing condition wording until a scenario needs a typed dimension. Unknown conditions remain explicit and never become zero/default temperatures.
- **Offer:** exact grade and variant, retailer, currency, spool mass, observation date, stock status, source, and quarantined flag. Material medians remain derived context; buying decisions use offers for the chosen product.
- **Source witness:** digest, page, source block/row/column, property label, number/unit tokens, condition role and reviewer. Keep a reviewed exception state for layouts that require visual interpretation.
- **Decision/test record:** scenario and release ID, selected grade/state, requirement results, record IDs, print recipe/treatment, operator/test method, outcome and limits. This can begin as an exported scenario companion; do not place private team results into public maker-source tables without a deliberate model.

IDs must remain stable. New vocabularies and relationships enter their schema in the same change. Retire or supersede incorrect facts; do not delete history. Re-read and hash-check source facts before migrations. The two observed test-temperature role errors are a targeted correction under that workflow, not permission to rewrite all unknown temperatures.

### 3.2 Shared evaluation result

Use a single pure result structure for all output lenses. Suggested shape:

```js
{
  releaseId, scenarioId, materialId, productId, stateId,
  verdict, eligible, unresolved, screened,
  requirements: [{
    requirementId, status, reasonCode, reason,
    evidenceScope, measurementIds, evidenceIds, profileIds, sourceIds,
    conditionCompatibility, admittedUnknownConditions,
    inferenceBasis, closeToLimit, nextAction
  }],
  manufacturing: { gates, treatments, route, unresolvedCapabilities },
  rank: { indexId, value, inputRecordIds, inputStateId, reasonIfUnranked }
}
```

This is an illustrative contract, not code to paste without design review. Preserve current statuses and supported interval semantics. The result must identify whether a pass uses maker measurements, a declared twin, printer-guide context or user assumptions. A scenario with user assumptions must remain visibly hypothetical even if it satisfies its entered limits. Estimates remain separate and may never confirm a product.

Material rollups derive counts from those results. Material-wide spreads remain useful context; the active ranked set uses only applicable passing product/state results. Chart-guide ranking, count-above-line, table sorting and exports must share that basis, or clearly label a different contextual calculation and refrain from calling it the candidate ranking.

### 3.3 Data-point debugging

`trace` and SQL should identify their input generation. A proposed `trace --scenario <file> --product <id> --requirement <id>` follows:

1. Requirement and evidence policy.
2. Product/state selected and alternatives considered.
3. Value/profile/evidence record and applicability.
4. Condition compatibility and any admitted unknowns.
5. Raw/typed parsing and headline preference rule.
6. Source hash, page/block and review reason.
7. Verdict, range/spread/estimate treatment and downstream rank.

Generated SQLite must reject raw/compiled generation mismatches, regenerate from the same inputs, or clearly run a compiled-only mode. It must not silently mix them. Machine-readable trace output enables tests and debugging tools without screen scraping.

### Phase 2 — Close selected data gaps and shorten the practical workflow

Work: F08/F09/F10/F11/F12. Use the acceptance portfolio to rank a small data worklist. For each gap: name the affected scenario, exact product/state, source question, expected decision benefit, and stopping rule. Exhausting a producer's published evidence without success is a recorded result, not a reason to infer a value.

UI structure:

1. A concise starting route for a part class plus limits and goal; no automatic structural requirement calculations without validated engineering input.
2. Machine/route and permitted-treatment intent visible beside the active question.
3. Compact result header: passing products/materials, unresolved alternatives, and explicit policy.
4. Passing product cards first, with state, recipe source, treatment, relevant properties and unresolved next task.
5. Material spreads, source tables and broad maker knowledge available as expandable context.
6. Compare selected products/states; retain material comparison for broad exploration.
7. Export the exact product/state decision brief and its remaining test tasks.

Give separate recovery messages for an all-missing requirement, an unsupported confirmation category, and measured failures. A sunlight/weather screen with zero failures and all unknown must say that the records cannot confirm it, rather than suggesting that no material suits the application.

Targets are proposed and should be confirmed by a quick team prototype: at 1024×768 show at least three useful candidate rows/cards without first scrolling past method exposition; open a chosen product and see its verdict, required treatment and first recipe fields in the initial drawer view. At 390×844 retain usable controls/reading without page-width overflow; prioritization of desktop engineering use is explicit.

Gate: keyboard-only filters/drawers isolate focus, Escape and return focus work; exports/imports preserve product/state, assumptions and release; malformed input leaves the current session intact; five representative engineers/operators can complete the intended task path or clearly identify the unresolved evidence, with recorded completion times and misunderstanding incidents. Five is a practical formative sample, not a statistical proof of usability.

## 5. Test strategy

Keep the current schema, raw reconciliation, cache, contract, snapshots, scale/reproducibility and rendered-fuzz suites. Give each a truthful purpose.

| Layer | What it should prove | What it does not prove |
|---|---|---|
| Source witness tests | Value/property/role/column binds to the intended saved source bytes, or a reviewed visual exception | Producer's measurement is physically correct |
| Schema and lint | Complete typed records, valid relations, raw/typed agreement, explicit missing states | Exposure/state is adequate for the user's service case |
| Independent scenario oracle | Approved product/state applicability and selection semantics on source-grounded cases | All possible applications |
| Engine unit/metamorphic tests | Interval, rollup, scope, condition and ranking invariants | Real H2C coupon behavior |
| Rendered parity and snapshots | UI faithfully presents engine results and handles recovery/round trips | Correctness of an engine policy it shares |
| Source spot check | A stratified human-read error estimate for sampled decision records with attribution | Exhaustive source accuracy |
| Team task trials | Comprehension, findability, error recovery and actionable handoff | Certified suitability |
| Team coupon tests | Local product/recipe/state performance under a documented test | Universal allowables across printers, lots and geometries |

Useful metamorphic tests: a failing grade cannot remove an unresolved viable grade under the new rollup; adding another product's positive exposure cannot confirm the target grade; forbidding a required treatment cannot improve eligibility; a grade's own contrary evidence cannot be hidden by a sibling's positive; stricter numeric limits cannot create new passes; sorting/view changes cannot change eligibility or the goal result; touching record-only content must move zero scenario answers.

Split self-consistency and independent acceptance results in reports. Every discovered semantic failure gets a small counterexample that fails on the old implementation; avoid tests that merely restate a helper's current output.

## 6. Release scorecard

Baseline metrics live in the evidence JSON and original snapshots. Generate new metrics from the corrected product/state model rather than copying the old counts.

| Goal | 2.1 release evidence |
|---|---|
| Defensible decisions | Independent portfolio approved; no known scope/state/feasibility/ranking false confirmation in that corpus |
| Visible uncertainty | Exact gaps and next actions on every unresolved selected product; no conflation of no-data with disproof |
| Useful coverage | Report scenarios settled and actionable product/state bundles added; raw source volume reported separately |
| Practical workflow | Team task record and before/after timings; passing product/recipe surfaced promptly on laptop |
| Reproducibility | Content release ID throughout; same-date changes warn; immutable artifact opens offline |
| Data operations | Generation-aware trace/SQL, recoverable apply, rehearsal and idempotence verified |
| Efficient loop | Cold/warm fast verification within90s; full gate retained; stage/scale/size budgets measured |
| Documentation | Clean-clone commands exercised; current task/authoring/debug guides match UI and contracts |

An answer-count decrease is acceptable when unsupported passes are removed. A coverage increase is valuable only if scope/state and source conditions support the moved decisions. Record human reviewers separately from agent reviewers.

## 7. Explicit deferrals

Defer a server database, accounts, full shared approval workflow, a framework rewrite, a universal weighted ranking, certification/allowables promises, generic cross-state correction factors, broad import expansion, and a new estimate-model algorithm without measured need. Keep the comprehensive record searchable, but do not load additional narrative into the active decision flow merely because it exists.

After 2.1 is in actual team use, consider richer service-state portfolios, dimensions/warpage tests, fatigue/creep, supplier refresh scheduling and shared local test evidence. Let observed decisions and failures choose their scope.
