# Contracts and the shared core

> **In short.** The remake's parts talk to each other through a few fixed shapes, called contracts. They are written as
> TypeScript types in `packages/domain/src/contracts/`. Types only describe data, and none of them runs. Beside them,
> `packages/domain/src/core/` holds one copy of four small rules that the old code repeats in several places. Tests
> check that each new copy gives the same answer as every old copy on the current data. Work package WP-07; the plan's
> section is 02 §9.

## The contracts

| Contract | File | What it is |
|---|---|---|
| `WriteCommand`, `CommandResult` | `write.ts` | One requested change to the data, and the answer: applied, a duplicate, or refused with a reason. A command always says what it expected to find (`expect`), so a change made against old data is refused as stale. A value correction or a new measurement must carry its evidence: source, page and quote. |
| `Actor` | `write.ts` | Who acted. A person, or an agent that always names its model (owner ruling OQ-17 A). |
| `ChangeRecord`, `ChangeSet` | `change.ts` | What a change did to one record (before and after, as the exact CSV text), and one exported file of such records. The file is named by date, topic and short hash, with no counter. In the workspace a record is `draft`, `exported` or `merged`. |
| `Proposal` | `proposal.ts` | One reading of a source page, before anyone accepts it. States: `pending`, `accepted`, `rejected`, `held`. A held proposal always says why. An AI reading names its model and prompt. |
| `EngineInput`, `RowResult`, `RequirementResult`, `Evaluation`, `ProductView` | `engine.ts` | What the engine reads and what it answers. `RequirementResult` is today's loose bag of fields. It is narrowed later, under parity (WP-18, WP-19). |
| `ScenarioV2`, `ScenarioV1`, `ScenarioHash` | `scenario.ts` | The question a person asks: as a saved file (version 2, or an old version 1 that still opens) and as a link with one-letter keys. |
| `PublicManifest` | `manifest.ts` | What a deploy publishes, with each file's digest, and which parts each mode needs before it may show a result. |
| `ReasonCode` | `reason-codes.ts` | A name for each sentence the old code writes to explain an answer. This is a placeholder (see below). |

## The words

`vocab.ts` holds the words the contracts share. Each word list is a list of values in `core/vocab.ts` or
`core/gate-verdict.ts`, copied from one named place in the old code, or the schema's own list, generated by WP-06:

- **Requirement status:** `PASS`, `FAIL`, `UNKNOWN`, `INDETERMINATE`. These are the engine's own spellings, so the
  parity checks compare like with like. A product's overall verdict is never `INDETERMINATE`.
- **Print gate verdicts:** `within`, `within-low-end`, `edge`, `exceeds-recommended`, `exceeds`, `unknown`, best first.
- **The six missing-value words:** from `schema/vocab/missing-states.csv`. A cell holds either a value or one of these
  words, never both, and the word is never treated as 0.
- **Groups:** `meets`, `one-check-away`, `not-enough-data`, `unlikely-to-meet`, `hidden`, `fail`.
- **Also:** the unknown policies, the evidence levels, the requirement kinds and operators a scenario may hold, the
  views and column sets, and the engine's own reasons for a missing value (such as `not-comparable`), which are not the
  six cell words.

`tests/domain/vocab.test.mjs` and `gate-verdict.test.mjs` fail when a list differs from the old code it is copied from,
in content or in order. The type test (`packages/domain/test/contracts.type-test.ts`) fails the type check when a
list differs from the schema's, or when a contract allows something it should forbid: a held proposal with no reason,
a value correction with no evidence (as a command or as a recorded change), a stale refusal without the expected and
current values, or a product row without its state.

## Distinct IDs

A material ID, a product (grade) ID, a measurement ID, a source ID and a requirement (constraint) ID are separate
types. The type checker refuses a product ID where a material ID is expected. A plain string becomes an ID only after
a check against the schema's pattern (`core/ids.ts`, tested equal to the schema). The type exists only while checking
and costs nothing when the code runs. The requirement ID is reserved for now: the old engine has no such ID, and it
arrives with WP-19.

Two places still carry plain strings. The compiled database's type (`Db`, WP-06) and a saved scenario do not
promise checked IDs, because the old code does not check them there. IDs are to be branded where data enters the
engine's contract, in the typed engine wrapper (WP-11), so the engine's outputs carry checked IDs.

## Reason codes

Today the engine explains each answer in an English sentence, and in two places it reads its own sentence back with a
text pattern (`constraints.js:948-949`). The plan is a code beside each sentence, plus a renderer that rebuilds the
exact old sentence from the code. `ReasonCode` lists one code for each place in the old code that writes a sentence,
with the file and line beside it. It adds no meaning that the sentence does not already have, nothing reads it yet,
and it will change when the renderer is built (WP-19, owner question TS-3).

## The shared core

| Rule | Module | Old copies it replaces |
|---|---|---|
| `tidy`: round a computed number to 12 significant figures | `core/tidy.ts` | 4: build products, engine ledger, engine constraints, page print-spread |
| `stateId`, `parseStateId`: a product state as text, such as `annealed:120:16+conditioned` | `core/state-id.ts` | 2 for `stateId` (build, engine), 1 for `parseStateId` |
| The gate-verdict table: each verdict's order, its answer, and whether it counts as within, at the low end, outside or on the line | `core/gate-verdict.ts` | About 9: build precedence and producers, engine status, page labels, print spread, material facts, filters, chamber need, validation report, schema |
| Tolerances: 23 ± 2 °C test temperature; 0.01 MPa test load; the estimate stage's 0.44 to 0.46 MPa band; the 5 °C low-end margin | `core/tolerances.ts` | 2 to 3 each: build products and compile, page material facts, estimate observations |

Nothing uses the shared core yet. The old code is frozen and keeps its own copies. The new engine and build will use
the shared core when they are ported.

## How we know the copies agree

`tests/domain/*.test.mjs` builds the current data (`dist/db.json`) and compares each shared rule with every old copy:

- `tidy`: every number in the build, plus sums, thirds and tenths of them.
- `stateId`: every product state, which must also equal the identifier the build stored.
- The gate table: every gate of every material, product and print profile, run through the engine, the page's
  counters and the build's aggregation.
- The tolerances: every stated test temperature and load, run through the build's `assess` and the page's `refusedBy`.

A copy that a module does not export is read from its source line. The test fails if that line moves or changes.

**Result on the current data:** every copy agrees. Two disagreements appear only on values the data does not hold.
They are recorded in [defects.md](defects.md) (WP07-D1, WP07-D2) under the owner's ruling Q2-19: behaviour is kept,
and fixes come later.

## Running the checks

```bash
npm run typecheck                  # the contracts and their type tests
npm run types:check                # generated types current, strong config
npm run types:ratchet              # no new casts or `any`
node --test tests/domain           # copies agree (builds dist/db.json first if it is missing)
```
