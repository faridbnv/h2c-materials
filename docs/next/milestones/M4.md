## Decisions made while building (for the owner's review)

1. **"Main unchanged" accepts one recorded exception.** `main` is no longer at the baseline commit `5eabafad`: it moved to `c31ceebf` when the tamper-proof gate (`.github/workflows/next-gate.yml`, owner option A of 2026-10-21) was added. `remake/baseline/main-allowed.json` lists that one path with its source. A change to any other path of `main` fails the candidate.
2. **Every defect now has a disposition** in `docs/next/defects.md` (16 entries). They are the agent's classification, not rulings: 13 known limitations (kept as the old tool has them, R-Q2-19), 2 fixed (WP20-D1 by commit `00bff6a9` of the M3 fixes, where the PR number replaces the commit when that branch merges; WP21-D1 by PR #40 with its transition), 1 owner-ruled (WP21-D2, R-OQ07). Five touch science and name R-Q2-19, R-OQ05, R-OQ06 or R-OQ07; none is fixed here.
3. **The restore needs its hold.** A restore without `DEPLOY_HOLD` set to the value the request names is refused, because the next push would deploy over it.
4. **A live restore after the cutover** is `gh workflow run next-main.yml --ref main -f mode=live -f restore=true`, against a standing request committed at the cutover (`OPERATING.md`).
5. **The weekly checks** (scale, reproducible build, 2,000 scenarios) moved into `next-main.yml`; they start after the cutover, because scheduled workflows run from the default branch only.

- The live deploy, the release job and the live restore cannot be rehearsed on the preview (limitations L-02 and L-03 in `known-limitations.md`).

- The crawl of the live site for `save-legacy.sh` uses the rebuilt manifest's paths plus the names the baseline receipt records: the WP-02 baseline holds output digests, not a per-file inventory.

## Close

What stood between the kit and `candidate:check`, and what was done (the M4 close PR).

**Blockers fixed**

1. **The records deadlock.** `candidate:receipt` read the owner's rows (`safari-check`, `bus-factor-rollback`, the `retire-approved` rows), the rehearsal, the legacy-zip record and the status files from the candidate commit, where they can never be: a commit cannot name its own sha. The receipt now reads them from the newest commit on `origin/remake/v3` (first-parent) that has the candidate as an ancestor and differs from it by `RECORD_PATHS` only, overlays those paths into the checkout, and records `records: { from: <sha> }`. A descendant that changes any other path is never the source; with no such descendant the records are the candidate's own. `observeNow` is unchanged: anything outside `RECORD_PATHS` still moves the candidate.
2. **The receipt is made on CI.** A receipt made on the owner's Mac fails parity and tests-parity only by the known host difference (L-07). `.github/workflows/candidate-receipt.yml` (ubuntu-24.04, `.nvmrc` Node, Chromium, 180 minutes) makes it. GitHub dispatches only workflows on the default branch, so it is started like a restore: by a push to `remake/v3` that changes `remake/control/receipt.json` (`{"schema":1,"sha":"<40 hex>"}`; `null` asks for nothing). The commit must be an ancestor of the pushed commit. The receipt is kept as an artifact and pushed to `records/receipt-<sha8>`; an agent opens the pull request from there. Only the last job writes; no secret; the sha reaches a shell only through `env`. `next-main.yml` does not read `receipt.json` as a restore request. The candidate must contain the records overlay, so the next candidate is the merge of this change.
3. **Status files.** WP-27, WP-30, WP-32, WP-34 and WP-35 are `done`, with their merged PRs. `checks:register -- --cutover-ready` now lists only the three rows owned by WP-29 (`S-context-audit`, `A-source-audits`, `A-doctor`).
